## 大原則: すべての数値は実測データを使う（2026-07-26ユーザー指定）
**推計・外挿・按分・平均の流用を一切しない。** レポートに載る売上・原価・広告費・数量は、必ずShopifyまたはMetaから当該期間を直接取得した値であること。効率化のために簡易処理をしてはならない（2026-07-26に30日広告費を「7日×30/7」で外挿し、卓上冷感クーラーを黒字472,286円→赤字84,521円と誤報告した）。
- 期間ごとに必要なクエリを省略しない。行数の節約より正確性を優先する（30日集計はキャンペーン別1本＝約20行で足りる。上限50,000行/月に対して誤差）
- バリエーションで原価が異なる商品は、**どの期間でも**バリエーション別の実数量で加重する（7日の構成比を30日に流用しない）
- 累積行も構成日の実測を積む（7日平均を1日分として足さない）
- どうしても実測が取れない項目がある場合は、数値を出さず「取得不可」と明記する。推計値を載せる場合は必ず「推計」とラベルする

## 集計は必ず「毎回ゼロから積み直す」（2026-07-27のバグで確定）
**累積値を前回値に足し込む繰り越し方式（アキュムレータ）を使ってはいけない。** 生成スクリプトは文言修正などで1日に複数回走るため、走らせた回数だけ当日分が多重計上される。2026-07-27に「7/18〜累積」を `cum.json` への加算方式で作っていたため、3回実行で7/26が3重計上され、9日累積の売上を13,041,944円→**16,290,866円**と誤って報告した。
- 累積・期間集計はすべて**日次実測のリストから毎回合計し直す**。同じ入力なら何回実行しても同じ結果になること（冪等）
- 累積行を出したら、**「構成日の日次合計と一致するか」をコード内で assert する**
- 中間ファイルに保存してよいのは「その日に取得した実測データ」だけ。**計算結果を次回の入力にしない**

## データの正（真実の優先順位）
- **売上 = Shopify の `gross_sales − discounts`（値引き後・返品は引かない）**（2026-07-20ユーザー指定＝net_salesの式から返品を除いた額）。全店の売上は商品テーブルの足し算ではなく**必ず全店を直接1クエリで取得**する。Metaの計上売上（コンバージョン値）は判断に使わない（下記「突合」参照）
  - **⚠️ 商品別の売上も `gross_sales − その商品の discounts`（2026-07-29ユーザー承認で変更）。** 従来は商品別をgrossのままにして値引きを全体サマリーで一括控除していたが、値引率が商品で0%〜9.1%と大きく違うため、**まとめ買いの多い商品（害虫ブロッカー・5WAY腰掛けファン・瞬間冷感ポンチョ）の効率が実態より良く見えていた**。
    - Shopifyの `discounts` は商品別に取得でき、**商品別の合計＝全店の値引きと1円まで一致する**（2026-07-29実測: 7日426,628／3日173,230／前日47,883／30日1,760,101）。毎回assertする
    - 切替により **商品別売上の合計＝全体サマリーの売上** になるため、全体サマリーでの一括控除は不要。照合は「**Σ商品利益 − カタログ広告費 = 全体利益**」（差0円）
    - **MERは下がり分岐は上がるので余裕は必ず縮む**。2026-07-29実測: 全店 MER 2.63→2.52・分岐 1.41→1.43・余裕 +1.22→+1.09。縮み幅は値引率に比例（5WAY−0.36／害虫−0.27／ポンチョ−0.24／4WAY−0.17／値引ゼロの携帯電動シェーバーのみ±0）
    - **増分MERも値引後ベースで測る**（商品×日別の `discounts` を取得して日次売上から引く）
  - **返品の扱いはA案で確定（2026-07-20ユーザー決定）: 売上からも利益からも控除しない**。代わりに**単月累計の返品額（returns）を毎回別建てで表示**して管理する。返品率>3%の商品はアラート
  - **⚠️ 原価は「販売数」で計算する（返品数を引かない）。2026-07-29ユーザー指定で修正。** 従来は `net_items_sold`（＝返品を引いた数）に単価原価を掛けていたため、**返品分の原価がCOGSから外れて利益が過大に出ていた**（A案は「売上からも利益からも控除しない」なので、原価だけ戻すのは規約違反の状態だった）。影響は2026-07-29時点で 7日+15,201円・3日+8,516円・前日+3,460円・**30日+79,520円**の原価増。
    - **販売数 = `gross_sales` ÷ 売価**（`gross_sales` は返品を引かないので「売れた数」が出る）。バリエーションで原価が違う商品は**バリアント別の gross ÷ そのバリアントの売価**で出す
    - 割り切れない場合は**窓内で売価が変わった商品**（例: ムダ毛シェーバー 7/27に5,980→6,980、湯上がりガーゼワンピース）。これらは返品ゼロを確認したうえで `net_items_sold` を販売数として代用し、代用したことをレポートに明記する
    - 検算: すべての商品で **販売数 ≥ net_items_sold**（差＝返品数）をassertする
    - **返品は商品別の損益計算に一切入れない。**商品別テーブルの「返品(7日)」列と全体の返品累計でのみ見る（壁掛けディスペンサーの返品率10.3%は2026-07-20ユーザーが原因解消済みと確認。以後の新規返品が減っているかを月次累計で追う）
  - **対象は広告出稿の有無に関わらずShopify LOOTYの全商品**（優先配送・ネックマッサージャー・リカバリーサンダル等の非広告商品も売上・原価・利益に含める。広告費ゼロ商品は利益=売上−原価）。ユーザー指定。従来（広告18商品のみのgross）と比べ、値引き控除で売上はやや下がり、非広告商品の加算で上がる方向の両効果がある
- **広告費 = Meta**（Supermetrics FA, アカウント `act_1124340806289175`）
- **原価 = Shopify** の variant `inventoryItem.unitCost`。**送料込み**（送料無料運営のため追加送料計算は不要）
- ROASはMeta表示値を信用せず、必ず **購入価値÷消化額** を自分で割り算する（同名キャンペーン合算時にMetaのROAS列が約2倍になるバグを確認済み）
- 決済手数料は**実効ブレンド率 3.452%**を全体サマリーでのみ言及（商品別テーブルには含めない）。**2026-08-01の月次再計測値**（直近100注文 #20031〜#20130・金額ベース）:
  - Shopify Payments **76.2%** × 3.25%（Advanced・国内カード）
  - KOMOJU スマホ決済（PayPay・メルペイ） **16.3%** × **4.1%**（KOMOJU 3.5% ＋ **Shopify外部決済取引手数料0.6%**（2026-07-25にShopify決済設定画面のスクショで実測確認。外部決済にはKOMOJU手数料と別にShopifyが0.6%を請求する。旧モデルの0.5%は誤り））
  - KOMOJU Paidy **7.5%** × **4.1%**（同上。Shopify設定画面で0.6%表示を確認）
  - 前回（2026-07-19実測）は SP 71.8% / スマホ決済 23.5% / Paidy 4.6% ＝ **3.490%**。今回 **3.452%（−0.038pt）**。Shopify Paymentsの比率が上がり、料率の高いKOMOJUスマホ決済が減ったため。30日売上38,734,461円に対し手数料は14,594円の減

## MER・分岐・目標は手数料控除前で統一（2026-07-28ユーザー確定）
一時導入した「実効分岐MER（値引+手数料込み）」は**判定基準としては採用しない**。MER・分岐MER・目標MER・増分MERのゾーンはすべて従来どおり**手数料控除前**で統一する。理由: 全体サマリーに手数料控除後利益が常設されており、そちらで現金は把握できる。基準を二重にすると判定の一貫性が壊れる。
- ただし**注記だけは残す**: 余裕（MER−分岐）< 0.20 の商品は、値引4.4%+手数料3.452%を配賦すると実質赤字圏のため⚠️を付ける（判定は変えない。例: 携帯電動シェーバー 余裕+0.17 ⚠️）
- k=0.9229 の計算は毎月1日の手数料再計測の参考値としてのみ保持

## 判定日と実験は budget-snapshots.csv から自動導出する（2026-07-28 v2.0）
手で管理していた実験辞書（EXP）とTODAYセットが誤りの単一源だった（P1窓とデータ被覆のズレ→パーカー誤判定）。**`scripts/experiments.py` が予算スナップショットの日次差分から、変更日・前後予算・方向・P1/P2窓（祝日/天候日除外・最大4日）・判定日（変更+3日後）を機械生成する**。日次ビルドはこの出力を使い、手書きの実験定義を禁止する。
- 判定日の発生: 予算変更 → +3日後（P2に3クリーン日）／CR投入・値上げ → +7日後／同一キャンペーンの再変更は前の実験を消費（S1b③）
- 基準変更のメタルール: **しきい値の変更は将来の宣言にのみ適用**。宣言済みの判定は宣言時の基準で執行する（例外: 宣言自体が誤データから計算されていた場合のみ訂正できる。2026-07-28のパーカーが該当）
- 消化率の評価は予算据置2日以上のキャンペーンに限る（増額候補の抽出でも同じ。減額直後は機械的に100%超に見えるため）

## 手順

### 1. Shopify売上（4期間、必ず「昨日」を終端にする）
`mcp__Shopify__run-analytics-query` で以下を期間別に4回:
```
FROM sales SHOW gross_sales, net_items_sold, discounts, returns GROUP BY product_title ORDER BY gross_sales DESC SINCE <開始日> UNTIL <昨日> LIMIT 35
```
期間: 前日（昨日のみ）/ 直近3日 / 直近7日 / 直近30日

### 2. Meta現在予算（毎日変わるため必ず当日読む）
ユーザーは日予算を毎日増減しているため、`data_query` で**昨日時点の広告セット別設定予算**を取得する:
```
fields: adcampaign_name,adset_name,adsetstatus,adsetdaily_budget,cost
昨日1日分 (custom, timezone=Asia/Tokyo)
```
- 予算は広告セット単位（全キャンペーンABO）。同一キャンペーンに複数広告セット（例: 形状記憶日傘の並行テスト）がある場合は別行で扱う
- **予算スナップショットの記録と差分検知（毎回必須）**: リポジトリの `data/budget-snapshots.csv` に当日の広告セット別予算を追記し、コミット＆プッシュする。前日スナップショットとの差分から「昨日どの広告セットの予算がいつ変わったか」を検出し、レポート冒頭の変化点に載せる
  - 注意: Supermetricsの `adsetdaily_budget` は**全日付に現在値を遡って表示する**（履歴ではない）。変更履歴はこのCSVの日次差分だけが正
  - 注意2: `data_query` の予算フィールドは**数時間の取り込み遅延**がある。当日の変更が反映されたかを確認するときは `campaign_and_resource_get`（campaign_id + campaign_detail_level="ad_groups"）でMetaを直接読む。返る `daily_budget` は**100円単位**（例: 700 = ¥70,000）
- **Metaの予算ペーシング仕様（2026-07-19事実確認済み）**: 日予算は**単日で最大+75%まで上振れ**する（2021年10月に25%→75%へ変更）。ただし**暦週（日〜土）の合計消化は「日予算×7」を超えない**＝週平均で設定予算に収束する。実データでも確認済み（7/12-18週: 害虫100.0%・ナノガラス99.9%・ワンピース99.7%）。したがって:
  - **単日の消化上振れ/下振れにアラートを出さない**。上振れ日＝Metaが機会（需要）を見た日のシグナル、下振れ日＝弱い日
  - 消化の評価は**「暦週累計消化 ÷（日予算×週内経過日数）」**で行う。週90〜105%が正常。週予算を超える心配は仕様上不要
  - 週の前半に大きく上振れした場合、週後半は自動的に絞られる（失速と誤読しない）
- **消化率の解釈は予算変更タイミングとセットで行う**: 増額直後の1〜2日は配信ペーシングが追いつかず消化率が低く出るのが正常。「消化率<85%＝配信律速」と判定してよいのは**予算が2日以上据え置かれている広告セットのみ**。増額直後の低消化率は「様子見」であり問題ではない
- 消化率<85%（予算据え置き2日以上）の広告セットは「増額しても効かない」ため増額提案の対象外にする
- **学習中の広告セット（開始7日以内かつ週50CV未達）は予算もCRも触らない**。消化は学習の進行とともに自然に伸びる。運用シーケンスは「①学習完了と消化率85%超を待つ → ②予算の天井に2日連続で張り付いたら+20〜30%増額 → ③失速サイン（余裕縮小・CTR低下）が出て初めて新CR投入」の順（予算が先、CRは失速後）

### 4. 商品⇄キャンペーン対応（確定済みマッピング）
基本は名前の部分一致で1:1。**類似名の混同に注意**:
- Meta「ディスペンサー」= Shopify「**壁掛け**ディスペンサー」（ユーザー確定済み。オートソープディスペンサーではない）
- 日傘2商品（形状記憶日傘／完全遮光・形状記憶・晴雨兼用・UV日傘）は**両方アクティブな別出品として個別に利益を算出する**（ユーザー指定）。ただし同一SKUで相互流入があるため、予算の増減判断時は「日傘2本合算のMER」も併記する
- シェーバー2種（携帯電動／ムダ毛）、ファン系（4WAY／旧・瞬間冷却／3WAY／卓上）も相互流入があるため突合チェックはグループで行ってよい
- 「カタログ全部（テスト）」は全商品横断のカタログ広告 → **広告費はどの商品にも配賦せず、全体サマリーで差し引く**
  - **ただし商品テーブルの最終行に「カタログ全部（テスト）※全商品横断」の1行を必ず出す（2026-07-29ユーザー指定）。** 広告費列を単純SUMしたときにカタログ分が抜けて総額が目減りするのを防ぐため。この行は広告費・日予算・Meta計上の実績（消化・購入件数・CPA・Meta基準ROAS）だけを埋め、売上/原価/利益/MERは「—」にする（Shopify側で商品に紐づかないため分解不能）。**商品テーブルの広告費列の合計＝Metaアカウントの実消化額** になることをレポートで明示する

### 5. 計算
各商品×各期間で:
- 原価合計 = 販売数 × 単価原価
- **バリアントで原価が異なる商品（壁掛けディスペンサーの2本¥2,144〜2,261/3本¥2,929セット等）は、`GROUP BY product_title, product_variant_title` でバリアント別販売数を取得して加重計算する**。原価表の単価をそのまま全数に掛けない
- 原価の正はShopifyのunitCost。ただしユーザーのCJ実費と乖離が疑われる場合（2026-07-18にディスペンサーで$18.3vs$13.7の乖離を検出、確認中）はアラートを出す
- **利益 = 総売上高(gross) − 原価合計 − Meta広告費**
- 利益率 = 利益 ÷ 総売上高、MER = 総売上高 ÷ 広告費
- 損益分岐MER = 総売上高 ÷（総売上高 − 原価合計）… これを下回ると赤字
計算はPythonスクリプトで行う（暗算しない）。

### 5c. 30日の商品別広告費は必ず実測を取る（2026-07-26のミスで確定）
**「7日実績 × 30/7」で外挿してはいけない。** 期間途中で開始したキャンペーンの広告費が過大になり、利益が大幅に過小評価される。2026-07-26に卓上冷感クーラー（7/13開始）を「30日で−84,521円の赤字」と誤報告した（実測では**+472,286円の黒字**、837,497円→280,690円と広告費を3倍に見積もっていた）。同じ誤りで5WAY・ポンチョ・ムダ毛も赤字に見えていた。
- 30日集計は `data_query` でキャンペーン別に**1本だけ**取る（`fields: adcampaign_name,cost,offsite_conversions_fb_pixel_purchase,offsite_conversion_value_fb_pixel_purchase`、日別は不要なので約20行）
- キャンペーンの `start_date` が30日窓の中にある商品は、レポートに「稼働N日」を併記する（30日利益を他商品と単純比較しない）

### 5b. 曜日分析（毎回実施）
`FROM sales SHOW gross_sales TIMESERIES day` の直近30日から曜日別平均売上と指数（全体平均=100）を計算する。2026-07-19時点の実測: **日曜125・土曜106・水曜100・金曜98・月曜93・木曜90・火曜87**（日曜が突出、火曜が最弱）。
- ヘッドラインの比較に**「vs同曜日平均」を必ず含める**（前日が火曜に低くても同曜日比で平常なら騒がない。逆に日曜なのに平日並みなら⚠️）
- 3日利益の比較も曜日構成を考慮して読む（例: 火水木の3日間は構造的に低く出る）
- 曜日指数は毎週月曜のレポートで最新値に更新して表を再掲する
- **曜日ごとの手動予算調整は不要**（Metaの週内ペーシングが自動で強い日に寄せている。上記ペーシング仕様参照）
- **祝日は曜日指数の計算から必ず除外する（2026-07-28に実装）**。7/20（海の日）を月曜平均に含めたままだと月曜指数が94.8になるが、除外すると**88.2**。この汚染により7/27を「同曜日比−5.0%で弱い」と誤報告した（実際は非祝日月曜平均比**+2.9%で平常**）。同曜日平均の比較も祝日除外の平均を使う
- **祝日の扱い（重要）**: 曜日指数は祝日を区別できない。**日本の祝日・連休中日は「週末扱い」（土日並みの売上=指数105〜125を期待）**で評価し、平日の曜日指数を適用しない。レポート冒頭で昨日・本日が祝日かを明記する（例: 2026-07-20は海の日で三連休の最終日）。祝日実績はその曜日の平均計算からも除外するのが望ましい（サンプルが歪むため、可能なら除外して算出）

### 5d. 天候は考慮しない（2026-07-28ユーザー確定）
気温・天候の補正やルールは**採用しない**（冬まで含めると運用が重すぎる。広告効率と季節感の肌感で十分、というユーザー判断）。冷感カテゴリの売上シェアが日次で27〜44%動く事実は観測済みだが、対処は既存の仕組みで足りる: 単日で意思決定しない・7日ローリング・曜日補正・祝日除外。Metaの自動入札が暑い日に配信を強めるため支出側は自動で追随する。

### 5e. 収益算定の照合を毎回実施する（2026-07-28監査で定型化）
毎朝のビルドで以下3本の照合をassertし、通らなければレポートを出さない:
1. **売上の縦照合**: Σ商品gross = 全店直接取得のgross（差0円であること）
2. **利益のエンドツーエンド照合**: Σ商品利益 − 全店値引 − カタログ広告費 = 全店サマリー利益（±0.1%以内。2026-07-28実測は差+507円=0.02%で、これはMeta当日データの確定ドリフト分＝説明可能）
3. **広告費の照合**: Σキャンペーン別 ≒ アカウントレベル（±0.1%。前日分は翌朝に必ず再取得する——当日値は確定まで+0.1%程度動く）

**既知のバイアス（毎月併記する・数値を直すのではなく開示する）**:
- **返品×数量の不整合**: 売上はgross（返品を引かない・A案）だが、数量net_items_soldは返品分を引いている → 返品された数量の原価が原価から消え、利益が「返品原価」分さらに過大。実測 約73,000円/30日（2,440円/日）。月次の返品累計の横にこの額を併記する
- **原価は常に現行単価で評価**（再調達原価ベース）。7/25改定前の期間も新単価で計算しており、30日利益は歴史的な現金と微差がある（意思決定用としては正しい）

### 5f. 商品別売上の定義は従来どおり（2026-07-28ユーザー判断で切替を見送り）
**商品別の売上は従来どおり gross（値引前）のまま。値引は全体サマリーで一括控除する。定義の変更はしない。**
一時「商品別も gross−実測値引 に統一」を提案・適用しかけたが、話が複雑になるためユーザー判断で見送り・原状復帰した。以下は事実の記録としてのみ残す（判定・定義には使わない）:
- 値引の正体はクーポンではなく自動割引「Quantity break（2個以上で10%OFF）」。まとめ買いされる商品ほど値引率が高い（7日実測: 害虫9.2%・ポンチョ7.1%・5WAY6.4% ↔ ムダ毛0.5%）
- 判定しきい値も従来のgross基準のまま（害虫1.28・ナノ1.23・5WAY 1.59 等）。勝手に基準を書き換えない

### 6. 突合サニティチェック（毎回実施）
商品ごとに Meta計上売上 ÷ Shopify総売上高 を出す。**75〜100%が正常帯**（Shopifyが上が正常）。
- 100%超は異常ではない: ①Metaはカート全体の金額をクリック商品に計上する ②Shopify純売上は値引き後でMetaは値引き前 ③類似商品間の相互流入 が原因
- **105%超 or 70%未満が続く場合のみ**フラグを立てる（ピクセル二重発火・マッピングずれ・カタログとの重複計上を疑う）

### 6b. なぜMERで判断するのか（毎回レポートに判断根拠として明記する・2026-07-26ユーザー指定）
**MERは「より正確なROAS」ではない。測っているものが違う。**

| | 計算式 | 分子の性質 |
|---|---|---|
| **ROAS** | Meta計上コンバージョン価値 ÷ 広告費 | Metaが「広告が生んだ」と**判定**した売上（アトリビューション＝推定値） |
| **MER** | **Shopify実売上 ÷ 広告費** | 実際に入金された売上（**実測値**） |

**MERを判断軸にする4つの理由**（2026-07-26実測を根拠として毎回レポートに載せる）:
1. **利益率と数式で直結する** — `利益率 = 1 − 原価率 − 1/MER`。だから目標MER・損益分岐MERが定義でき、予算判断がそのまま利益率の判断になる。ROASは分子がMetaの推定値なので、この式に代入できない
2. **商品別ではMetaの計上がズレる** — 7日実測の突合率は**79%〜108%**（4WAY 79%・健康サンダル79%・スリッパ108%）。カート単位計上・商品間の相互流入・カタログ広告への振り替えが原因。予算配分は商品単位で行うため、この精度では使えない
3. **Metaの数字は自己申告** — 広告媒体が自分の成績を自分で採点している。過去に同名キャンペーン合算でROAS列が約2倍になるバグも確認済み
4. **取りこぼしがない** — MERは分子が全売上・分母が全広告費。カタログ広告のように商品配賦できない費用（7日208,595円）も分母に入るため、全体の帳尻が必ず合う

**MERの弱点と、それを埋める増分MER**: MERの分子には広告が生んでいない売上（オーガニック・リピート・指名検索）も入るため、広告の**貢献度は過大**に出る。2026-07-26実測ではMetaが全店売上の96%を計上しており非広告流入は約4%（385,277円）だが、これはMeta側の申告値。したがって:
- **MER**＝「この商品は全体として儲かっているか」→ 継続/停止の判定に使う
- **増分MER**＝「追加した1円が効いたか」→ 予算の増減判定に使う
この2層で使い分ける。MER単独で増額を決めない。

### 7. 判定ルール（期間の役割分担）
**大原則（ユーザーと合意済み）: 意思決定は7日ローリングのみ。毎日=監視、3日=警戒、30日=戦略。ユーザーが手を動かすのは「今日が判断日」の商品だけ**。
原則: 判断に必要なのは期間でなく**購入約50件分の証拠**。判断遅延のコスト＝日次広告費×赤字幅なので、消化額が大きい商品ほど早く判断する。
- **前日**: 監視のみ。消化急増・購入ゼロの異常検知。単日で意思決定しない
- **3日**: 悪化の連続性確認（3日連続赤字→要注意リスト入り）
- **7日**: **意思決定の基本単位**（テコ入れ着手・増額のトリガー）
- **30日**: 撤退判断には使わない。増額の安定確認・商品育成・季節計画に使う

**提案の一貫性ルール（2026-07-24ユーザー指摘で確定）**: 予算・CRの提案は**判定日にのみ**出す（判定日前の前倒し提案をしない）。判定日の**合格基準は前日までに数値で宣言**し（例:「増額後3日MER≥4.0なら+24%」）、当日は宣言した基準に当てはめるだけにする。一度出した提案を新データなしに翻さない。すべての推奨には数値根拠（余裕・消化率・出血額/日・機会損失額）を添える。

**判定カレンダーの管理（毎回必須）**: 各商品に「次回判定日」を割り当てて管理する。判定日の発生ルール:
- 増額実施 → 3〜4日後にMER維持の判定日
- テコ入れ実施（減額・新CR・値上げ等）→ 7日後に効果判定日
- 新商品 → 購入50件到達見込み日が判定日
- 撤退プロトコル進行中 → 各段階の期限日
- 上記に該当しない健全な商品 → 判定日なし（監視のみ）
判定日が来ても証拠不足（CV件数が少ない等）なら延期し、理由を明記する。

**撤退プロトコル（段階式。一発判定しない）**:
1. **即日〜3日（事故停止）**: 購入ゼロで分岐CPA×3消化、CPM急騰2倍などの明確な異常 → 即減額・停止
2. **7日（テコ入れ着手）**: 7日利益マイナス（MER＜分岐）→ 原因分解で修正を1回打つ。**予算の扱いは出血規模で決める（2026-07-23ユーザーと合意）**:
   - 診断が素材疲弊（頻度>2.5／CTR低下／素材6週間以上／CVR維持）かつ**日次赤字が予算の15%未満** → **CR追加・予算据え置き・7日後判定**でよい（据え置きの方がCVが集まり判定が速い。半減してもCRテスト自体は継続される＝減額とCRは対立しない）
   - 日次赤字が予算の15%以上、または**テコ入れ2サイクル目**（1回目の修正後も赤字継続）→ **半減を併用**（テストを半額で受ける）
   - 診断が需要減衰（CTR正常でCV減／季節の谷／全開放でCPM上昇）→ CRでは直らない。減額・停止が正解で、CR追加は判断を遅らせるだけ
   - CTR低 → クリエイティブ差し替え
   - CVR低 → LP・オファー改善
   - CPM高 → 即断せず3段階で検証: ①頻度（>2.5なら疲弊）②配信面の偏り（publisher_platform×platform_position別CPM）③ターゲティング設定。**設定が既に全開放（Advantage+ ON・絞り込みなし）ならCPMはその商品の買い手層の相場**であり広告設定では下がらない。打ち手は (a)訴求替えCR（Advantage+では素材＝実質のターゲティング）(b)値上げ・AOV改善で高CPMを回収できる経済性にする (c)高CPM×高原価率の構造なら停止。なおCPM自体の高低は問題ではない（例: 4WAYはCPM¥6,000でMER5超）。見るべきは常にMERと分岐の差
3. **テコ入れ後さらに7〜14日（撤退判断）**: 分岐割れが2サイクル連続 → 停止提案
4. **新商品**: 購入50件到達まで確定判断を保留（日販件数から到達予定日を明記する）

**増額**: 7日MERが損益分岐を大きく超え（余裕+1.0以上）かつ30日でも安定、**かつ増分MERが目標ライン以上**なら +20〜30%の段階増額を提案。増額後は数日ごとにMER維持を確認

### 7b. 利益率35%を北極星にした運用（2026-07-25ユーザー方針）
ユーザー方針: **利益率35%は必達目標ではなく「常に目指す姿勢」**。したがって**利益率のために利益額を捨てる打ち手は提案しない**。利益額と利益率が同時に上がる打ち手だけを積み上げる。

**目標ラインの計算**: `利益率 = 1 − 原価率 − 広告費率` より、利益率35%を満たす広告費率は `1 − 原価率 − 0.35`、その逆数が**目標MER**。

> **目標MER = 1 ÷ (1 − 原価率 − 0.35)**　　損益分岐MER = 1 ÷ (1 − 原価率)

**⚠️ 目標MERは商品ごとに計算する（2026-07-26に誤りを修正）。** 全店の原価率から出した単一値（当時2.91）を全商品に当てるのは誤り。原価率は商品で18.9%〜46.8%と大きく違うため、目標MERも**2.17〜5.49倍と2.5倍の開き**がある。全店値を使うと、低原価率の優良商品（害虫・ナノガラス）を「効率不足」と誤判定して増額機会を潰す。全店の2.91は**全体サマリーの評価にだけ**使う。

### 7c. 利益率の3分解と「何日で見るか」（2026-07-25ユーザー要望）
**`利益率 = 1 − 原価率 − 広告費率`** に必ず分解して出す。MERとは `利益率 = 1 − 原価率 − 1/MER` で対応しており**同じ情報を別角度で見たもの**だが、用途が違う:
- **利益率**: この商品はいくら稼いでいるか。**商品間で直接比較できる**（MERは原価率が違うと比較できない）
- **原価率 / 広告費率**: 稼げない**原因の切り分け**。同じ「利益率が低い」でも打ち手が正反対になる
- **MER / 余裕**: 広告が損益分岐を超えているか →**継続/停止**の判定
- **増分MER**: 次の1円を足すべきか →**予算の増減**の判定

**ボトルネック判定（毎回自動でラベル付け）**: 原価率>33% → 原価交渉・値上げで手当て（広告をいじっても直らない）／広告費率>40% → 減額・CR・LPで手当て／両方超 → 赤字、撤退プロトコルへ。
実例（2026-07-25）: 害虫はMER2.82・利益率43.0%、パーカーはMER3.47・利益率35.0%。**MERが高い方が利益率は低い**——差は原価率（21.6% vs 36.1%）。

**値上げ判断の定型計算**: 許容できる数量減 `y = 1 − (売価−原価) ÷ (新売価−原価)`。原価率が高いほど値上げ耐性が大きい（例: ムダ毛は+1,000円で23.9%減までOK、UV歯ブラシは14.8%減まで）。原価率>40%の商品には必ずこの数字を添える。

**⚠️ 黒字化ラインは「その時点の7日販売数」で大きく動く。古い件数を使い回さない（2026-08-02に判明）。** 3WAYの黒字化ラインを7/31時点は「30件」基準で17.3%と記載していたが、8/2時点の直近7日は**46件**で、同じ式でも**46.0%**になる。件数が増えるほど広告費を粗利で吸収しやすくなるため許容幅は広がる。**値上げを提案するたびに、その日の直近7日の件数と広告費で計算し直す。**

**⚠️ ただし上の `y` は「粗利総額が不変」のラインであって「黒字化」のラインではない（2026-07-31に区別を追加）。** 日予算は固定なので広告費は数量に比例して減らない。**2本立てで示す**:
- **改善ライン `y = 1 − (売価−原価)/(新売価−原価)`** … これ以内なら今より良くなる
- **黒字化ライン `z = 1 − 広告費 ÷ (件数 × (新売価−原価))`** … これ以内なら分岐を超えて黒字になる
- 必ず `z < y`。実例（3WAY・**8/2時点の7日実測 111,678円/46件**、5,980→6,980円）: **黒字化 46.0% / 改善 22.2%**。「22.2%まで大丈夫」だけ言うと黒字化しない領域を見落とす

**「何日平均で見るか」は日販個数で決まる（5日実測）**:
- **日販20個以上** → 日次のブレは4〜8pt。**3日平均で判断可**（誤差2〜4pt）。該当: 4WAY・害虫・形状記憶・ナノガラス・完全遮光・パーカー・卓上
- **日販10〜20個** → 3日はやや粗い。7日で見る
- **日販10個未満** → ブレが13〜64ptで**7日でも利益率は当てにならない**。利益率ではなく**7日累計の金額（黒字/赤字）とMER・CPAで判断する**。該当商品では3日利益率を「−」で出す
- 目安の式: 必要日数 ≈ (日次標準偏差 ÷ 5pt)²

**判定保留（増分MERが測れない）商品の扱い**: |Δ広告費|<3,000円/日で測定不能な商品は、**次に予算を動かすとき意図的に±25%以上動かして測定可能にする**（13k以下の商品は±20%では3,000円に届かない）。

### 7e-1. 「やるべきこと」の出し方（2026-07-27ユーザー指摘で全面変更）
ユーザーから「打ち手が並んでいるだけで、つまり何をすればいいか分からない」と指摘された。**選択肢を並べるのは分析であって指示ではない。** 以下の形式を厳守する。

**① 今日やること（広告）— 最大3件**
判定日の商品だけ。内容は「予算変更」と「CR追加」のみ。ゼロなら「本日は操作なし」と言い切る。

**② 今週の1件（広告以外）— 必ず1件だけ**
価格・原価・LP・AOVの打ち手は**週に1件しか出さない**。達成が確認できるまで毎日同じものを載せ続ける。選定は次のスコアの最大値:

> **スコア = 効果額（円/週） × 残シーズン週数 ÷ 着手工数（時間）**

**③ タスクは必ず5点セットで書く**: 商品／具体的な作業（クリックできるレベル）／所要時間／期限／期待効果（円）。「LP改善」「原価交渉」だけでは指示にならない。

**④ CVRの評価は「自店内比較」だが、価格を無視しない（2026-07-28に更に修正）**
CVRの単純順位は価格帯を混同する（8,980円の商品は3,980円の商品よりCVRが低くて当然）。**売上/クリック**（＝AOV×CVR）と**同価格帯内のCVR比較**で評価する。2026-07-28実測: UV歯ブラシはCVR順位15位だが売上/クリックは**329円で店内2位**＝LPに問題なし（前日のLP改善提案を取り消した）。3WAYも売上/クリック234円で中央値209円超え＝取り消し。**LP改善対象は売上/クリック下位かつ同価格帯内でも劣後する商品のみ**: ディスペンサー113円・サングラス135円・卓上152円・携帯シェーバー154円

**（旧④）CVRの評価は前週比ではなく「自店19商品の分布での順位」で行う（重要）**
前週比だけで「CVR悪化→LP改善」と書いてはいけない。2026-07-27にこの誤りで、バランスケアスリッパ（CVR 3.21%＝**9位/19・中央値以上**）と携帯電動シェーバー（3.18%＝**10位/19**）に不要なLP改善を提案した。前週が異常に高かっただけだった。
- 毎回 `購入 ÷ アウトバウンドクリック` を全商品で自算し、**中央値と順位**を出す
- **中央値以上 → LPは触らない。** 前週比が−30%でも触らない
- **下位25%（15位以下）→ ここで初めてLP/商品ページの改善対象**
- 2026-07-27実測の中央値 **3.18%**。下位: ディスペンサー1.42%(19位)・卓上冷感クーラー1.93%(18位)・ワンピース2.14%(17位)・UV歯ブラシ2.60%(16位)・3WAY2.75%(15位)
- 外部の業界平均は取得できないため使わない。**同じ流入源・同じ国・同じ価格帯の自店内比較が最も精度の高いベンチマーク**であることを明記する

**⑤ 残シーズン週数を打ち手の選定に必ず使う**
効果が出るまで時間のかかる手を、シーズンが終わる商品に提案しない。
- **残5週未満 → 即効性のある手のみ**（値上げ・LP・広告）。**原価交渉・CJ数量交渉は提案しない**（交渉〜反映に3〜4週かかり回収できない）
- **残8週以上／通年 → 原価交渉が最も効率的**
- 2026-07-27時点の残シーズン: 卓上冷感クーラー・4WAY・5WAY・瞬間冷却HF・3WAYサーキュレーター **5週**（〜8/31）／パーカー・アームカバー・ポンチョ・UVハット **6週**／日傘2種・サングラス **7週**／害虫ブロッカー **9週**（〜9/30）／ムダ毛・ナノガラス・UV歯ブラシ・携帯シェーバー・スリッパ・ディスペンサー・健康サンダル **通年**

### 7d-0. 予算の増減は「変化型3日シグナル」で回す（2026-07-30ユーザー提案をバックテストで検証して採用・最優先）
ユーザー提案「強いシグナルなら3日で上げる／弱いシグナルなら3日で下げる」を6/29-7/29の全商品・全日で検証した結果、**期間の3日は正しく、トリガーの取り方が間違っていた**。実測:

| 検証 | 結果 |
|---|---|
| 予測力（過去N日MER → 次のN日MER の相関） | 3日 r=+0.569 ／ 7日 r=+0.596 → **ほぼ同じ。7日にする理由はない** |
| **水準**型・弱（3日MERが分岐割れ）→ 次の3日も分岐割れ | **24%**（7日でも36%）→ 下げ判断に使えない |
| **水準**型・強（3日MERが目標超え）→ 次の3日も目標超え | 58%。かつ**4週で70回発動**し複利で暴走（ナノガラス9回=5.2倍・害虫8回=4.3倍）→ 増額トリガーに使えない |
| **変化**型・悪化（3日MERが自分の直近7日ベースライン比 −25%以下） | **72%的中** |
| **変化**型・改善（同 +25%以上） | **68%的中** |

→ **水準（MER vs 分岐/目標）は「状態」であって「イベント」ではない。**常時点灯するので3日ごとの操作トリガーにすると先週の暴走（8商品同時増額→全店利益−54万円/週）を再生産する。**変化（自分の直近ベースラインからのズレ）をトリガーにすると精度が3倍**になる。

**採用する運用ループ（毎日チェック・操作は3日単位）**
```
指標 = 直近3日の曜日補正MER ÷ 直前7日（変更前）の曜日補正MER
  ≤ 0.75（−25%悪化）→ 🔻 −20〜30% 減額
  ≥ 1.25（+25%改善）→ 🔺 +20〜30% 増額（上げ幅は1回+30%以内）
  その間            → 触らない
ガード（これが無いと暴走する）
  ① ロックは「変更後3クリーン日（祝日除く）＋その判定」まで。判定に通れば次の段へ進んでよい
     ※2026-07-31改定。旧「7日ロック」は測定のために置いたが、5WAY・アームカバー級のΔでは
       増分MERがそもそも測定不能（標準誤差が判定幅を超える）ため、待っても何も測れず機会損失だけ残る。
       判定は増分MERではなく「変更後の1日あたり利益 ≥ 変更前の1日あたり利益」で行う
  ② 増額の同時実行数は制限しない。代わりに**ポートフォリオ上限**で縛る:
     直近7日間の日予算の純増合計 ≤ 全店日予算の+5%（2026-07-31時点で 545,250×5% = 27,262円/日）
     ※旧「同時2商品まで」は商品数で縛っていたため、小さい商品2件で枠が埋まり大きな機会を落とした。
       壊したのは「商品数」ではなく「増やした総額」（W3→W4で+404,322円/週＝+11%）なので金額で縛る
  ③ 季節終盤（残4週未満）の夏物は増額対象外
  ④ 3日連続赤字は「事故」ではない（実測36%的中・その後4日の合計は+75,511円と黒字）。
     単日・3日の赤字だけで減額しない。減額は必ず変化型シグナルか7日利益マイナスで判断する
  ⑤ CR判定と予算判定は分離する。CRの良し悪しは**同一広告セット内の広告どうしのCPA比較**で見る
     （同じ予算・同じ配信条件を共有するため予算変更の影響を受けない）。
     「余裕」「MER」など予算に依存する指標をCR判定の基準にしない
```
- 水準（MER vs 分岐/目標）は**健康状態の表示**として残す（シンプル判定シートの4状態）。**操作の引き金にはしない**
- 撤退プロトコル（7日利益マイナス→テコ入れ→2巡目で停止）は従来どおり併存。こちらは構造判断、変化型シグナルは日々のチューニング
- 実装: `scripts/signal3.py`（変化型シグナルの日次計算）。定例レポートの「シンプル判定」シートにシグナル列を追加する

### 7e-0. シンプル運用ループを正面に置く（2026-07-30ユーザー方針・最優先）
ユーザーの目的は一つ:**「売れるなら広告を出す。売れないなら下げる・直す。3日・7日の効率で判断して、悪ければ改善する」**。分岐の議論やルールの解釈で本題が埋もれてはいけない。したがって:
- **Excelの先頭シートは「シンプル判定」**にする。全広告商品を1行ずつ: 7日MER／3日MER／前日MER／分岐／目標／7日・3日・前日利益／消化率／状態／今やること(1行)
- 状態は4つだけ: **🚨縮小・停止**（7日MERが分岐割れ or 7日利益マイナス）／**🔧改善**（3日MERが分岐割れ、または7日・3日MERが分岐+0.3未満の弱含み）／**🚀伸ばす候補**（7日MER≥目標 かつ 消化率≥95%）／**✅維持**（それ以外）
- チャット本文もこの順で話す: ①今日やること ②状態が動いた商品 ③理由は聞かれたら。**V1〜V9・S1〜S5などの内部記号をチャットに出さない**（フローは背景の品質保証であり、会話の主役にしない）
- 判断の時間軸は変えない: **7日=決定、3日=警戒、前日=監視**。単日で意思決定しない
- 詳細な検証（増分MER・測定力・診断D1〜D5）は判定の**裏付け**として後ろのシートに置く。結論が変わるときだけ本文で触れる

### 7e. 出力の簡潔さ（2026-07-25ユーザー指摘）
分析の分量が増えたことで「結局何をすればいいか分からない」という状態が起きた。**レポートの冒頭または末尾に「ネクストアクション」を必ず独立して置く**:
- **今日やること**を最大3件、1行ずつ（商品名・具体的な変更内容・所要時間）。ゼロなら「本日は操作なし」と1行で言い切る
- **次の判定日**を日付順に1行ずつ（日付／商品／合格基準／不合格時の処置）
- 診断・根拠・多角的な打ち手は**この後ろに置く**（読まなくても行動できる状態にする）
- 商品別の推奨アクションはExcelの「推奨アクション」列を正とし、**チャット本文では全商品を展開しない**（動きのある商品だけ）

### 7e-2. 減額の前に必ず原因分解する（2026-07-26ユーザー指定）
**「余裕≤0だから減額」と直行してはいけない。** 減額判定に入ったら、まず週次でCTR/CVR/CPM/頻度を前週と比較し、原因に応じた打ち手を予算据置で先に打つ。減額が正解なのは「需要減衰」と診断されたときだけ。

**毎回取得する診断指標**（`data_query` を週次で2〜3本。fields: `adcampaign_name,cost,impressions,link_CTR,CPM,Frequency,outbound_clicks,offsite_conversions_fb_pixel_purchase`。CVR = 購入 ÷ outbound_clicks で自算する）:

| 診断 | 条件 | 打ち手（予算は据置） |
|---|---|---|
| **D1a 配信面の拡大** | **CPA悪化 ≥+15% かつ インプレッション +30%以上 かつ 頻度の変化 ±10%以内**（＝同じ人に何度も出したのではなく、新しい人へ配信を広げた）。**CTRの水準は問わない** | **原因は予算増。CRでは直らない。**予算を戻すか、広がった先の成績を受け入れるかの二択。D1より先に判定する |
| **D1 素材疲弊** | **CTRの2週間累積変化が −15%以下**、かつ D1a に該当しない（「2週連続低下」だけでは判定しない。−0.2%→−5.5%のような誤差でトリガーするため。2026-07-26にこの誤りで形状記憶日傘・3WAYに不要なCR提案を出した） | **その広告セットにCRを追加**する。**既存CRは止めない** → 7日後に再判定 |
| **D1b 単一CR** | その広告セットで配信中のCRが1本だけ **かつ 悪化の先行指標①〜④のいずれかが出ている** | 予備CRを1本足す（予算・既存CRは触らない）。**日予算の小さいセットから試す** |
| **D2 頻度過多** | 頻度 > 2.5 | ①オーディエンス拡大（類似%↑/全開放）②新CR ③配信面を広げる |
| **D3 LP/オファー** | CVR 前週比 −15%以下 **かつ 自店CVR順位が下位25% かつ 売上/クリックも下位25%**（価格帯を打ち消した指標でも劣後していることを確認する。単価が高い商品はCVRが低くて当然のため） | ①LP改善（ファーストビュー・レビュー・配送日数）②価格/送料訴求 ③優先配送の見せ方 |
| **D4 CPM上昇** | CPM 前週比 +15%以上 | ①全開放(Advantage+) ②配信面の偏り確認 ③訴求替えCR ④値上げで高CPMを回収できる経済性にする |
| **D5 需要減衰** | CTR・CVR・CPM・インプレッションすべて横ばいでCPAだけ悪化 | **ここで初めて減額。**CRでは直らない。季節終盤なら段階縮小 |

複数該当する場合はD1a→D1→D2→D3→D4の順で対処し、いずれも当てはまらずCPAだけ悪化しているときのみD5（減額）に落とす。**診断結果と根拠の数値（CTR何%→何%等）を必ずレポートに明記する。**

**⚠️ D1aの判定条件からCTRの門を外した（2026-07-29修正）。** 旧版は「CTR −15%以下」を通過した場合にのみD1aを検討していたため、CTRが−13.8%の4WAYと、**CTRがむしろ+18%上がっている5WAY腰掛けファン**が D5（需要減衰＝減額が正解）と誤ラベルされた。5WAYは7/19に開始したばかりで「需要が減衰した」は明らかに成立しない。CPA悪化の原因が「配信面を広げたこと」なのか「素材が擦り切れたこと」なのかは、CTRではなく**インプレッション増 × 頻度横ばい**で判別する。実装は `scripts/daily/calc*.py` の `DIAG` 生成部。

**同一広告セット内の負けCRを手動で止めない（2026-07-26ユーザー指摘・実データで確認）。** Metaは同一広告セット内なら自動で勝ちCRに配信を寄せる。UV歯ブラシ除菌器では7/23に複製リセットを投入した2日後にMetaが自動でB→A-コピーへ切り替え、CPAが11,569円→3,050円に改善した（手動操作なし）。ムダ毛シェーバーでも A(109円)/B(27,766円)/C(3,907円) と自動配分されている。**CR施策は「足す」だけでよく、「止める」作業は不要。**

**🚨 D1bを「予防投入」の根拠に使ってはいけない（2026-07-31のミスで確定・実測コスト約87,000円）。** 旧D1bは「CTR劣化がなくても、**日予算の大きいセットから順に**予備CRを足す」と書いてあり、これは同じSKILLの上位ルール「**健全な商品（余裕が安定〜拡大中）はCRも触らない**／CR投入のトリガーは悪化の先行指標①〜④が出たときのみ」と**正面から矛盾していた**。2026-07-27に4WAY（口座最大の日予算85,000円）へこの矛盾したルールで予備CRを投入した。

投入判断時（7/27）の4WAYを先行指標に当てるとこうだった:
| トリガー | 実測 | 該当 |
|---|---|---|
| ①頻度 > 2.5 | 1.18 | ✗ |
| ②CTR 2週連続低下 | 7/6-12 5.50% → 7/13-19 5.71%（**上昇**） | ✗ |
| ④7日利益の2週連続減少 | 7/10-16 719,277 → 7/17-23 840,707（**増加**） | ✗ |
→ **完全に健全。投入してはいけない状態だった。**

実測コスト（7/29-31・Shopify実測で補正）: 広告A CPA 1,635円 / 広告B CPA 2,705円。Bの消化137,117円がAの満額配信時CPA（7/28実測1,769円）で回っていれば77.5個、実際は50.7個。**差26.8個 × 粗利3,250円 ＝ 約87,000円／3日（日2〜3万円）**。ユーザーが2026-07-31に広告Bを停止。

**新CRの失敗コストは日予算に比例する。** 探索フェーズでMetaが新CRに配分を寄せる（4WAYでは7/30に85.9%）ため、大きい予算ほど損が大きい。したがって:
- **予防的なCR投入をしない。**必ず先行指標①〜④のどれかが出てから
- 素材コンセプトを試したいときは**日予算の小さい商品で先に検証**する。口座上位の予算を持つ広告セットで新CRを試さない
- 「疲弊したときの受け皿がない」は投入理由にならない。受け皿は**疲弊が観測されてから**用意する（先行指標は疲弊の数日前に出るので間に合う）

**🚨 例外が確定した（2026-07-31・UV歯ブラシと4WAYの2件）: 「勝ちCRのCPMが上がってインプが激減し、Metaが安い負けCRへシェアを移している」ときは負けCRを止めるのが正しい。** この形は素材疲弊ではないので、放置すると勝ちCRが締め出されたまま戻らない。

**判別手順（勝ち側の4指標を日別で見る）**:

|---|---|---|
| 頻度 | **上がる**（>2.5） | 下がる or 横ばい（低いまま） |
| CTR | **下がる** | **上がる** |
| CVR | 維持 | **上がる** |
| インプ | 緩やかに減 | **激減（−60%以上）** |
→ 頻度もCTRも疲弊を否定しているなら、CPM上昇は**配信量が絞られて一番濃い層にだけ出ている状態**（= 予算を奪われた副作用）。**負けCRを止めて勝ちCRに予算を戻す。**

**⚠️ 広告セット・広告の話をするときは必ず `adsetstatus` を同時に取得し、停止済みを除外する（2026-07-31のミスで確定）。** 7日集計の消化額だけを見て「ディスペンサー0520類似5%を停止せよ」と提案したが、**その広告セットは7/25に既にPAUSED**で、7日窓に7/24-25の消化が残っていただけだった。今後は:

- 「停止せよ」と書く前に **最終消化日が昨日かどうか**を確認する

**CPM上昇は「配信面の構成シフト」と「同一面の単価上昇」に必ず分解する（2026-07-31追加）。** 打ち手が正反対になる。`publisher_platform,platform_position` 別に前週と当週を取り、構成をW4・単価をW3に固定した反実仮想CPMを作って寄与を切る。2026-07-31実測:

### 7g-3. 値引きの正体は Quantity break（2026-07-29に50注文で再実測）

## 「カタログのCPA高騰＝夏物需要の減退」は成り立たない（2026-08-04・実測で棄却）

ユーザーの仮説「カタログのCPAが上がっている＝そもそも夏物需要が減退しつつあるのでは」を検証した。
Meta日次×キャンペーン（6/22〜8/03、779行）を週次に集計し、カタログ／季節物／通年物に分けて
`CPA = CPM ÷ (CTR × CVR × 1000)` に分解した結果、**仮説は棄却された。**

### 判別のシグネチャ
- **需要そのものの減退** = CTRが下がり、**CPMも下がる**（オークションが冷え、買い手が減る）
- **広告側の疲弊** = CTRが下がるが、CPMは横ばい〜上昇（同じ人に当て続けている）
- **クリックの質の劣化** = **CTRは上がるのにCVRが下がる**（興味は引けているが買う人ではない）

### 結果（6/22週 → 7/27週）

| 区分 | CPM | CTR | CVR | CTR×CVR | CPA | 診断 |
|---|---|---|---|---|---|---|
| カタログ | +34.3% | **+23.6%** | **−36.2%** | −21.2% | +70.5% | クリックの質の劣化 |
| 季節物（14商品） | −2.2% | −7.4% | −11.8% | −18.3% | +19.8% | 広告疲弊型 |
| **夏物のみ（害虫除く13商品）** | **−1.7%** | **+6.6%** | −7.4% | — | **−0.4%** | **劣化していない** |
| 通年物（8商品） | −5.5% | −15.7% | −13.1% | −26.8% | +29.1% | **需要減退型（CTR↓CPM↓）** |

**夏物13商品のCPAは6週間で −0.4%＝ほぼ横ばい。CTRはむしろ +6.6% と上がっている。**
夏物需要は減退していない。カタログの悪化を夏物需要のせいにはできない。

### 本当に劣化しているのは通年物
通年物（ナノガラス・ムダ毛・携帯シェーバー・ディスペンサー・UV歯ブラシ・健康サンダル・スリッパ・車載ホルダー）は
CPM −5.5% と CTR −15.7% が同時に起きている＝**需要減退型のシグネチャ**。
ただし通年商品に季節はないので、減っているのは市場の需要ではなく**LOOTYが到達できる残りの人数**＝需要プールの逓減。
ナノバブルで特定したのと同じ現象が、通年商品群の全体で起きている。

### 非広告流入は増えている（需要減退の反証）
Shopify実測の週次セッション: 6/22週 direct 8,210 + search 771 = 8,981 → 7/27週 13,900 + 816 = **14,716（+63.9%）**。
広告費あたりに直しても direct は 2.88件/千円 → 3.58件/千円 で **+24.4%**。
需要が減退しているなら広告に依存しない流入こそ最初に落ちる。増えている。

### カタログのCVRが崩れたのは7/25
日次で見ると、7/14-24（11日）は クリック4,195・購入173・**CVR 4.12%**、
7/25-8/03（10日）は クリック3,373・購入94・**CVR 2.79%**（−32.3%）。
z ≒ 3.2（p<0.002）で有意。単日ノイズではなく7/25を境にした段差。
同じ日に季節物・通年物のCVRは崩れていない（季節物 −5%、通年物 +13%）ため、
**LP側の変更（関連商品セクション等）が原因なら全campaignに出るはずで、出ていない＝カタログ固有の事象**。
最有力はカタログの商品セット・配信面のドリフト（アルゴリズムが成約しにくい商品へ露出を寄せた）。
7/25-26はカタログのCPMも4,844/4,868円とこの系列の最高値をつけており、配信先が変わったことと整合する。

### 運用への反映
1. **カタログの減額判断は「需要減退だから」ではなく「7/25以降クリックの質が崩れたから」**が正しい理由。
   30,000円 → 10,000円に下げ、浮いた20,000円を新商品テスト3枠に回す（新商品探索の項を参照）
2. **夏物の段階縮小を前倒ししない。** CPAが横ばいである以上、シーズン終盤の縮小はカレンダー通り（残6週）でよい
3. **本丸は通年物のプール逓減。** 通年物のCPAを戻す打ち手は素材でも予算でもなく、
   到達できていない層に届く新しい訴求か、新商品でプールそのものを増やすこと
4. **今後この3区分（カタログ／季節物／通年物）の週次ファネルを毎週月曜に出す。** `scripts/pool0804.py` を流用する。
   全店MERが落ちたとき、どの区分の話なのかを最初に切り分けないと打ち手を間違える

**壊れ方が違う＝原因が2つある。**
- **増額群は CTRとCVRが同時に落ちている**＝Metaが予算を消化するために薄い層まで配信を広げた。

- **据え置き群は CTRがほぼ無傷（−1.2%）なのに CVRだけ −33.4%**＝配信も訴求も効いているが、

2. **据え置き群は予算を触っても直らない。** UV歯ブラシとディスペンサーは既に停止済み、

   増額しないまま走らせ、シーズン終了とともに畳む。**新CRも投入しない（CTRは無傷なので効かない）
3. **新商品は正しい方向。** 8商品が効率をプラスに押し上げている。テストは止めず、むしろ3並列に増やす
4. **全体の日予算 559,000円は、6/08週水準（日345,317円）に対して +61.9%。**
   増分MERが分岐を割っている以上、この水準は正当化されていない。ただし夏物のCPAは横ばいなので
   一律に戻すのではなく、増額群の中で増分MERが分岐（1.396）を割っているものから順に戻す

### この分解を今後の定型にする
全店MERが落ちたときは、必ず ①シフトシェア（既存 vs 新規 vs 構成） → ②増額群 vs 据え置き群の
CTR/CVRの壊れ方 の順で切り分ける。この2段を飛ばすと「全部だめ」に見えて打ち手を間違える。

## 「需要プールが尽きた」は言い過ぎだった — 到達人数の実測で修正（2026-08-04）

ユーザーの疑問「需要プールってこんな簡単に尽きるものなの？」を受けて、リーチ（重複排除の到達人数）で検証した。
**結論: 尽きていない。私の言い方が不正確だった。** `scripts/pool_test0804.py`

### 検証A — 古典的な飽和（同じ人に当て続けて飽きられた）は起きていない
アカウント全体 2026-01-01〜08-03（7ヶ月・消化38,865,406円）: **到達 4,096,042人 / 頻度 3.74回**。

7ヶ月かけて1人あたり3.7回しか見せていないので、「飽きられた」では説明できない。ユーザーの指摘が正しい。

### 検証B — リーチは今も安く伸びている。落ちたのは届いた相手の質
継続13商品（6/08週 → 7/27週）:

つまり「新しい人に届かなくなった」のではない。**届いた新しい人が買わなくなった。**

### 正しい言い方
- LOOTYは7ヶ月で **4,096,042人** に到達し、そのうち買ったのは **19,736人（0.48%）**。
  残り **4,076,306人** は「Metaが買いそうだと判断して見せた上で、買わなかった人」
- 日本のMeta人口から見れば410万人はまだ一部。**母集団は尽きていない**
- 尽きかけているのは母集団ではなく、**Metaの予測モデルが上位にランクする層**。
  Advantage+は確度の高い順に配信するので、予算を積むほどランキングの下へ降りる。
  下の層は「まだ見ていない人」だが「Metaが買わないと予測している人」でもある
- **だからこれは永続的な枯渇ではない。ランキングを引き直せば戻る。**
  引き直す手段は3つ: ①新しい素材（Advantage+では素材＝実質のターゲティング）

- **季節**: 形状記憶日傘の6月は梅雨＝ピーク。7月末との比較には季節の下げが混ざる
- **予算の急変による学習リセット**: 6月→7月で日予算を大きく動かしている
次にこの3つを切り分ける。**「需要プールの逓減」と断定的に書かないこと。**

## 「中途半端な減額」は利益も情報も生まない（2026-08-04・実測で確認）

ユーザー指摘「減額とかある程度やったよな？」を受けて実測。**やってはいるが、量が足りず、効果も測れていない。**

- 日予算: ピーク 590,000円（7/26-27）→ 8/04 552,000円 → 本日の操作後 559,000円。**−5.3%**
- 実消化: 7/21-27 日 559,172円 → 7/28-8/03 日 544,463円。**−2.6%**
- その間のMER: **2.562 → 2.268（−11.5%）**。売上は日 1,432,722 → 1,234,762（−13.8%）。両期間とも火〜月の7日で曜日構成は一致

この期間の増分MERを計算すると **13.46** になるが、**採用してはいけない**:
1. 分母が全体の2.6%しかない。SKILLの既存ルール「|Δ広告費|が小さい対象は増分MERを算出しない」は全店にも適用される
2. 同じ期間にカタログのCVR崩壊（7/25）が起きており交絡している

**したがって「減額したから悪化した」とも「減額が足りない」とも、このデータからは断定できない。**

## 日傘の一本化 — URLリダイレクト案の評価（2026-08-04・ユーザー提案）

ユーザー案: 短いタイトルの商品を非公開にし、短い側の広告のリンク先を長いタイトルの商品に向ける。

### 学習リセットの答え
**広告の遷移先URLはクリエイティブの一部なので、Metaで編集すると「重要な変更」扱いになり
その広告セットは学習フェーズに戻る。** つまり Meta 側でURLを書き換えると学習はリセットされる。

**回避策: Metaを一切触らず、Shopify側でリダイレクトする。**
1. Shopify の URLリダイレクトで `/products/sun-umbrella` → 長いタイトルの商品ハンドル を作る
2. 短いタイトルの商品を非公開（または アーカイブ）にする → リダイレクトが有効になる

広告のURLは1文字も変わらないので**編集ゼロ＝学習リセットなし**。クリックは全部勝っているページに着地する。
順序を逆にすると一時的に404が出て広告が否認されうるので、**リダイレクトを先に作ってから非公開にする**。
実施後は必ず実際に広告リンクを1回クリックして着地を確認する。

### この案は私の「停止案」より良い

|---|---|---|
| 広告費 | 414,676 | 242,522 |
| クリック | 6,062 | 3,089 |
| **CPC** | **68.4円** | 78.5円 |
| CVR（Shopify注文÷クリック） | 3.07% | **3.53%** |

**短い側はクリックを13%安く買えている。壊れているのはCVRだけ。**
CPC/CTRは広告クリエイティブが決めるのでURLを変えても変わらない。CVRは着地ページが決めるので直る。
**リダイレクトは壊れた半分だけを直し、良い半分（安いクリック）を残す。停止案は両方捨てる。**

効果の見積り（短い側のCVRが 3.07% → 3.53% になった場合）:
6,062クリック × 3.53% = 214注文（現在186）→ 個数250 → 利益 **+503,074円/週**（現在386,911）＝ **+116,163円/週**

### ただしこの案が解決しないもの

- **(A) 着地ページが弱い** → リダイレクトで直る
- **(B) 2本のキャンペーンが同じ商品・同じオーディエンスで自社競合している** → リダイレクトでは直らない

(B)の証拠: 形状記憶のCPMは 2,044 → 2,801（+37.0%）、完全遮光も +30%。**全店のCPMは下がっているのに日傘だけ上がっている。**
ただし「日傘のオーディエンスがもともと競合が激しい」可能性も否定できず、(B)は仮説のまま。

**順序: (A)を先にやる。** ゼロリスク・可逆・学習リセットなし。7日測ってCVRが収束するかを見る。
その結果で(B)（＝片方を止めるか）を判断する。両方同時にやると何が効いたか分からない。

### 分担（例外なし）

**Metaから取ってよいのは配信指標だけ**（Shopifyに存在しないもの）:
`cost` / `impressions` / `CPM` / `link_CTR` / `outbound_clicks` / `Frequency` / `reach`

**必ずShopifyから取るもの**:
`gross_sales`（売上）/ `net_items_sold`（個数）/ `orders`（注文数）/ `discounts` / `returns`
**単価は必ず `gross_sales ÷ net_items_sold`。** variant priceの確認は `search_products` の `price`。

**Metaから取ってはいけないもの（損益計算に使用禁止）**:
- `offsite_conversions_fb_pixel_purchase` — 「注文数」であって「個数」ではない。さらに実測比 約91%
- `offsite_conversion_value_fb_pixel_purchase` — カート全体の金額。商品売価ではない
- MetaのROAS列 — 自己申告

この2つは**突合サニティチェック（Meta計上率が70〜105%か）にのみ使う**。使うときは必ず「Meta計上」と明記する。

### 混合指標の定義（分子と分母のソースが違うもの）
| 指標 | 定義 |
|---|---|
| MER | Shopify `gross_sales − discounts` ÷ Meta `cost` |
| CPA（注文） | Meta `cost` ÷ **Shopify `orders`** |
| CVR | **Shopify `orders`** ÷ Meta `outbound_clicks` |
| CPC | Meta `cost` ÷ Meta `outbound_clicks` |
| RPM（判別式） | 粗利/個（Shopify） × CTR（Meta） × CVR（上記） × 1000 |

### まとめ買い商品は「1注文あたり粗利」で判定する
`分岐CPA(注文) = 粗利/個 × 個数/注文`
害虫ブロッカーは 1.71個/注文なので、1個分の粗利3,127円と比べると必ず赤字に見える。
正しい分岐は **5,342円/注文**。該当商品: **害虫ブロッカー・壁掛けディスペンサー**。
レポートには `個数/注文` の列を必ず出し、1.2を超える商品には注文ベースの分岐CPAを併記する。

### 機械ガード: `scripts/datarules.py`
分析スクリプトは必ず `from datarules import *` して使う。
- `check_meta_fields(fields)` — Metaクエリに禁止フィールドが混ざっていたら理由付きで例外
- `Product` クラス — 売上系はShopify、広告費はMetaを受け取る。`price` / `gp_unit` / `gp_order` /
  `cpa_order` / `cvr` / `mer` / `mer_be` / `profit` を実装済み。**手計算しない**
- `reconcile(product, meta_orders)` — 突合率だけを出す。判断には使わない

### Shopifyで分解できないケース（唯一の例外）
Shopifyは**広告セット単位・クリエイティブ単位・キャンペーン単位に売上を分解できない**。
同一商品を2本のキャンペーンで回している場合（日傘）や、カタログ広告のように商品横断の場合は、
比率だけMetaから取る。**その数値は必ず「Meta計上・推計」とラベルする。**
判定は必ず Shopify で取れる単位（商品合算）で行う。

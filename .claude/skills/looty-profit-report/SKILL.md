# LOOTY 商品別損益レポート

## データの正（真実の優先順位）
- **売上 = Shopify** の `gross_sales`（**総売上高・値引き前**。ユーザー指定）。`discounts`/`returns` も取得し、値引き率>8% または 返品率>3% の商品はアラート表示。Metaの計上売上（コンバージョン値）は判断に使わない（下記「突合」参照）
- **広告費 = Meta**（Supermetrics FA, アカウント `act_1124340806289175`）
- **原価 = Shopify** の variant `inventoryItem.unitCost`。**送料込み**（送料無料運営のため追加送料計算は不要）
- ROASはMeta表示値を信用せず、必ず **購入価値÷消化額** を自分で割り算する（同名キャンペーン合算時にMetaのROAS列が約2倍になるバグを確認済み）
- 決済手数料 約3.4% は全体サマリーでのみ言及（商品別テーブルには含めない）

## 手順

### 1. Shopify売上（4期間、必ず「昨日」を終端にする）
`mcp__Shopify__run-analytics-query` で以下を期間別に4回:
```
FROM sales SHOW gross_sales, net_items_sold, discounts, returns GROUP BY product_title ORDER BY gross_sales DESC SINCE <開始日> UNTIL <昨日> LIMIT 35
```
期間: 前日（昨日のみ）/ 直近3日 / 直近7日 / 直近30日

### 2. Meta現在予算（毎日変わるため必ず当日読む）
ユーザーは日予算を毎日増減しているため、`data_query` で**昨日時点の広告セット別設定予算**を取得する:
```
fields: adcampaign_name,adset_name,adsetstatus,adsetdaily_budget,cost
昨日1日分 (custom, timezone=Asia/Tokyo)
```
- 予算は広告セット単位（全キャンペーンABO）。同一キャンペーンに複数広告セット（例: 形状記憶日傘の並行テスト）がある場合は別行で扱う
- **予算スナップショットの記録と差分検知（毎回必須）**: リポジトリの `data/budget-snapshots.csv` に当日の広告セット別予算を追記し、コミット＆プッシュする。前日スナップショットとの差分から「昨日どの広告セットの予算がいつ変わったか」を検出し、レポート冒頭の変化点に載せる
  - 注意: Supermetricsの `adsetdaily_budget` は**全日付に現在値を遡って表示する**（履歴ではない）。変更履歴はこのCSVの日次差分だけが正
  - 注意2: `data_query` の予算フィールドは**数時間の取り込み遅延**がある。当日の変更が反映されたかを確認するときは `campaign_and_resource_get`（campaign_id + campaign_detail_level="ad_groups"）でMetaを直接読む。返る `daily_budget` は**100円単位**（例: 700 = ¥70,000）
- **消化率の解釈は予算変更タイミングとセットで行う**: 増額直後の1〜2日は配信ペーシングが追いつかず消化率が低く出るのが正常。「消化率<85%＝配信律速」と判定してよいのは**予算が2日以上据え置かれている広告セットのみ**。増額直後の低消化率は「様子見」であり問題ではない
- 消化率<85%（予算据え置き2日以上）の広告セットは「増額しても効かない」ため増額提案の対象外にする
- **学習中の広告セット（開始7日以内かつ週50CV未達）は予算もCRも触らない**。消化は学習の進行とともに自然に伸びる。運用シーケンスは「①学習完了と消化率85%超を待つ → ②予算の天井に2日連続で張り付いたら+20〜30%増額 → ③失速サイン（余裕縮小・CTR低下）が出て初めて新CR投入」の順（予算が先、CRは失速後）

### 2b. Meta広告費（日別×キャンペーン別）
`data_query` (ds_id=FA, ds_accounts=act_1124340806289175, timezone=Asia/Tokyo):
```
fields: date,adcampaign_name,cost,offsite_conversions_fb_pixel_purchase,offsite_conversion_value_fb_pixel_purchase
直近30日 (date_range_type=custom, 昨日終端)
```
→ `get_async_query_results` で取得し、4期間に自分で集計する。

### 4. 商品⇄キャンペーン対応（確定済みマッピング）
基本は名前の部分一致で1:1。**類似名の混同に注意**:
- Meta「ディスペンサー」= Shopify「**壁掛け**ディスペンサー」（ユーザー確定済み。オートソープディスペンサーではない）
- 日傘2商品（形状記憶日傘／完全遮光・形状記憶・晴雨兼用・UV日傘）は**両方アクティブな別出品として個別に利益を算出する**（ユーザー指定）。ただし同一SKUで相互流入があるため、予算の増減判断時は「日傘2本合算のMER」も併記する
- シェーバー2種（携帯電動／ムダ毛）、ファン系（4WAY／旧・瞬間冷却／3WAY／卓上）も相互流入があるため突合チェックはグループで行ってよい
- 「カタログ全部（テスト）」は全商品横断のカタログ広告 → **広告費はどの商品にも配賦せず、全体サマリーで差し引く**

### 5. 計算
各商品×各期間で:
- 原価合計 = 販売数 × 単価原価
- **バリアントで原価が異なる商品（壁掛けディスペンサーの2本¥2,144〜2,261/3本¥2,929セット等）は、`GROUP BY product_title, product_variant_title` でバリアント別販売数を取得して加重計算する**。原価表の単価をそのまま全数に掛けない
- 原価の正はShopifyのunitCost。ただしユーザーのCJ実費と乖離が疑われる場合（2026-07-18にディスペンサーで$18.3vs$13.7の乖離を検出、確認中）はアラートを出す
- **利益 = 総売上高(gross) − 原価合計 − Meta広告費**
- 利益率 = 利益 ÷ 総売上高、MER = 総売上高 ÷ 広告費
- 損益分岐MER = 総売上高 ÷（総売上高 − 原価合計）… これを下回ると赤字
計算はPythonスクリプトで行う（暗算しない）。

### 6. 突合サニティチェック（毎回実施）
商品ごとに Meta計上売上 ÷ Shopify総売上高 を出す。**75〜100%が正常帯**（Shopifyが上が正常）。
- 100%超は異常ではない: ①Metaはカート全体の金額をクリック商品に計上する ②Shopify純売上は値引き後でMetaは値引き前 ③類似商品間の相互流入 が原因
- **105%超 or 70%未満が続く場合のみ**フラグを立てる（ピクセル二重発火・マッピングずれ・カタログとの重複計上を疑う）

### 7. 判定ルール（期間の役割分担）
**大原則（ユーザーと合意済み）: 意思決定は7日ローリングのみ。毎日=監視、3日=警戒、30日=戦略。ユーザーが手を動かすのは「今日が判断日」の商品だけ**。
原則: 判断に必要なのは期間でなく**購入約50件分の証拠**。判断遅延のコスト＝日次広告費×赤字幅なので、消化額が大きい商品ほど早く判断する。
- **前日**: 監視のみ。消化急増・購入ゼロの異常検知。単日で意思決定しない
- **3日**: 悪化の連続性確認（3日連続赤字→要注意リスト入り）
- **7日**: **意思決定の基本単位**（テコ入れ着手・増額のトリガー）
- **30日**: 撤退判断には使わない。増額の安定確認・商品育成・季節計画に使う

**判定カレンダーの管理（毎回必須）**: 各商品に「次回判定日」を割り当てて管理する。判定日の発生ルール:
- 増額実施 → 3〜4日後にMER維持の判定日
- テコ入れ実施（減額・新CR・値上げ等）→ 7日後に効果判定日
- 新商品 → 購入50件到達見込み日が判定日
- 撤退プロトコル進行中 → 各段階の期限日
- 上記に該当しない健全な商品 → 判定日なし（監視のみ）
判定日が来ても証拠不足（CV件数が少ない等）なら延期し、理由を明記する。

**撤退プロトコル（段階式。一発判定しない）**:
1. **即日〜3日（事故停止）**: 購入ゼロで分岐CPA×3消化、CPM急騰2倍などの明確な異常 → 即減額・停止
2. **7日（テコ入れ着手）**: 7日利益マイナス（MER＜分岐）→ 原因分解で修正を1回打ち、**同時に予算を半減**して出血を止める
   - CTR低 → クリエイティブ差し替え
   - CVR低 → LP・オファー改善
   - CPM高 → 即断せず3段階で検証: ①頻度（>2.5なら疲弊）②配信面の偏り（publisher_platform×platform_position別CPM）③ターゲティング設定。**設定が既に全開放（Advantage+ ON・絞り込みなし）ならCPMはその商品の買い手層の相場**であり広告設定では下がらない。打ち手は (a)訴求替えCR（Advantage+では素材＝実質のターゲティング）(b)値上げ・AOV改善で高CPMを回収できる経済性にする (c)高CPM×高原価率の構造なら停止。なおCPM自体の高低は問題ではない（例: 4WAYはCPM¥6,000でMER5超）。見るべきは常にMERと分岐の差
3. **テコ入れ後さらに7〜14日（撤退判断）**: 分岐割れが2サイクル連続 → 停止提案
4. **新商品**: 購入50件到達まで確定判断を保留（日販件数から到達予定日を明記する）

**増額**: 7日MERが損益分岐を大きく超え（+1.0以上目安）かつ30日でも安定 → +20〜30%の段階増額を提案。増額後は数日ごとにMER維持を確認

### 季節ローテーション方針（ユーザーの運営方針）
季節商品の入れ替えは**意図的な戦略**。「季節物だから撤退」ではなく、以下で運用する:
- 判断は必ず**シーズン内の直近7日利益**で行う（シーズン跨ぎの30日平均に引っ張られない）
- シーズン終盤（夏物なら8月中旬〜）: MERが損益分岐+0.3を切ったら段階減額 → 分岐割れで停止。在庫評価も添える
- 次シーズン商品のテスト開始は**シーズン到来の3〜4週間前**（例: 秋物は8月中、冬物は10月中）。早すぎる投入は失敗する（真夏に保温プレートを出して赤字になった実例あり）
- 新シーズン商品の選定基準（害虫ブロッカーの勝ち型）: 原価率30%以下・単価¥4,000〜6,000・「悩み解決」型訴求・シーズンピークが2ヶ月以上続くもの
- レポートには毎回「シーズン移行ステータス」（終盤商品の縮小状況／次シーズンのテスト状況）を1行入れる

### 8. 出力フォーマット（日本語・簡潔に）
0. **最上部: 昨日の全体実績×期間比較**（商品別テーブルとは別枠・ユーザー指定）。昨日の売上・原価・広告費・利益・利益率を、各期間の**日次平均**と並べて評価できる表で出す:

   | 指標 | 昨日(M/D) | 3日平均/日 | 7日平均/日 | 30日平均/日 | 昨日vs7日平均 |
   |---|---|---|---|---|---|
   | 売上 / 原価 / 広告費 / **利益** / 利益率 | … | … | … | … | ±X% |

   評価基準（利益のvs7日平均）: ±15%以内=✅平常／−15〜30%=🟡注意／**−30%超=⚠️要因分析を1行添える**（どの商品が沈んだか）。+30%超も🎉で要因を添える（何が伸びたか＝再現のヒント）。利益率が30日平均から3pt以上悪化していたら原価・広告費のどちらが原因かを明記
1. **冒頭: 前回からの変化点・アラート**（新たな赤字転落、急落/急伸、突合異常、前回提案と実際の予算変更の差分）
2. 全体サマリー（4期間の 売上/広告費/利益、カタログ広告費差引後）
3. 商品別テーブル（**7日の売上・原価・広告費・利益を必ず4列で表示**（ユーザー指定。利益だけの表示は不可）＋**前日は売上と利益の2列**（ユーザー指定）＋3日・30日の利益、7日MER、分岐、余裕、判定: 🚀増額/✅維持/🔧テコ入れ/🚨赤字、**現予算→提案予算**）
4. **日予算提案**: 広告セット単位で「現予算→提案額」と一言理由。ルール: 増額は+20〜30%/回まで・余裕+1.0以上かつ消化率85%以上が条件／**減額・半減は余裕+1.0未満の商品のみ**（余裕+1.0以上は悪化トレンドでも予算を触らず素材・LPで手当てする。勝ち配信の予算変更自体がコストという原則）／段階②対象は半減／総額は原則±10%以内に収め、構成の組み替えで対応
5. **今日の判断事項**（判定日が到来した商品のみ。「商品名／判断内容／7日データに基づく推奨／根拠」の形式。**ない日は「本日の判断事項なし」と明記**し、無理にアクションを作らない）
6. **監視のみ（次回判定日つき）**: 判定待ちの商品を「商品名: 次回判定日 M/D（何を判定するか）」で一覧化
7. 推奨アクション（判断事項以外の推奨があれば優先順・根拠つき、3個まで）
